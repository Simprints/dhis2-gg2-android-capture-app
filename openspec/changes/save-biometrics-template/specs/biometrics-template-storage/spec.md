## Purpose

The biometric face template(s) generated by Simprints during enrollment are
currently discarded after matching. The client wants them retained in DHIS2
for future analytics and reporting on biometric matching, so this capability
persists the template(s) to a hidden tracked entity attribute using the same
pattern already used for the biometric GUID and NHIS number.

## ADDED Requirements

### Requirement: Biometric template is persisted to a single tracked entity attribute
The app SHALL persist the biometric face template(s) returned by Simprints
for a TEI to a single, dedicated tracked entity attribute, distinct from the
existing biometric GUID attribute.

#### Scenario: Enrollment returns biometric templates
- **WHEN** a biometric enrollment for a TEI completes and returns one or more face templates
- **THEN** the templates are written to the configured template tracked entity attribute for that TEI

### Requirement: Multiple templates from the same enrollment are all retained
Simprints returns more than one face template per enrollment (multiple
captured frames). The app SHALL retain all templates returned for a single
enrollment, not only the first or last one.

#### Scenario: Enrollment returns two templates
- **WHEN** a biometric enrollment returns two face templates for the same subject
- **THEN** both templates are retained in the stored attribute value, and neither is dropped or overwritten by the other

### Requirement: Template attribute is hidden from manual data entry
The app SHALL hide the template attribute from the user-facing form. The
value SHALL only ever be written programmatically, never entered or edited
by a user.

#### Scenario: User views the enrollment or TEI form
- **WHEN** a user opens the enrollment form or TEI data entry form for a TEI with a Person tracked entity type
- **THEN** the template attribute is not shown as an editable or visible field

### Requirement: Template is written on registration flows that produce a biometric identity
The app SHALL write the template attribute for a TEI whenever that TEI's
biometric enrollment completes with a valid credential, whether the TEI was
newly registered from scratch or created via "register last" after a
biometric search.

#### Scenario: New registration without prior biometric search
- **WHEN** a user registers a new TEI and completes biometric enrollment during that registration
- **THEN** the template attribute is written for that TEI

#### Scenario: Registration via "register last" after a biometric search
- **WHEN** a user performs a biometric search, chooses "New person"/"New patient", and confirms "use last biometrics"
- **THEN** the template attribute is written for the newly created TEI using the biometrics captured during that search

### Requirement: Template write behavior on identity confirmation of an existing TEI is out of scope
Confirming the identity of an **already existing** TEI selected from
biometric search results (a flow distinct from "register last", handled
separately from enrollment) SHALL NOT write or update the template
attribute. Only the registration flows in the previous requirement write
this attribute.

#### Scenario: Confirming identity of an existing TEI from search results
- **WHEN** a user selects an existing TEI from biometric search results and confirms their identity (without registering a new TEI)
- **THEN** the template attribute for that TEI is left unchanged
